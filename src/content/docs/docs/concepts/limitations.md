archix makes a rolling-release system declared, locked and reversible, on top of pacman and a normal filesystem, by building every switch as a [deployment](/docs/concepts/atomicity/) that the next boot starts. Some of that has a price, and some guarantees stop short. This page lists them, so you know where the edges are.

## Switching

**Changes take effect at the next boot, and only then.** A switch never changes the running system: new packages, `/etc` files, services, sysctl and firewall rules all arrive when you reboot into the new deployment. That includes `archix install htop`; until the reboot, `htop` isn't there. Applying changes live is not planned for the first release. Dotfiles, other files outside `/etc`, `/usr` and `/opt`, and Flatpak apps are the exception: a switch writes them right away. See [What takes effect when](/docs/concepts/safety/#what-takes-effect-when).

**Changes to `/etc` before the reboot are merged, with edges.** The new deployment has its own copy of `/etc`, and the [`/etc` merge](/docs/concepts/safety/#changes-to-etc-before-the-reboot) carries what you change in the running one into it until shutdown. A file changed on both sides keeps your version, with the deployment's beside it as `.pacnew` for you to compare; nothing merges their contents. Managed files the switch rewrote, `/etc/ld.so.cache`, `/etc/mtab` and pacman's keyring stay as the deployment has them. After a power cut, the next boot carries what the old `/etc` held on disk, so a change made in the last moments before it can be lost. Two accounts on one UID or GID stop the account files from being carried until you renumber one. A rollback carries only changes made after it, `install --temp` none, and where systemd isn't running, as in a chroot, nothing is merged.

**Hibernation is off while a deployment waits.** Resuming the running system's memory image under the new deployment's kernel would mix the two, so from a switch's commit until the reboot, archix turns hibernation, suspend-then-hibernate and hybrid sleep off. Suspend still works.

**Plain pacman and yay can't change the system.** `/usr`, `/opt` and `/boot` are mounted read-only, so `pacman -S`, `pacman -Syu` and `yay` fail, and so does anything else that writes there at runtime, such as `sudo npm install -g`, an installer script that writes to `/opt`, or a file copied into `/usr/local/bin`. Install with [`archix install`](/docs/reference/cli/#install--s), or `archix install --temp` to try something without declaring it, and declare files under `/usr/local` in [`files`](/docs/reference/options/#files); both take effect at the next boot. Reading works as before: `pacman -Q`, `-Ss`, `-Si` and `-F`. See [pacman and yay](/docs/concepts/pacman-and-yay/).

**systemd-boot only, with the ESP outside `/boot`.** archix boots each deployment from its own systemd-boot entry, and refuses to switch without [`boot.loader = "systemd-boot"`](/docs/reference/options/#bootloader). GRUB and Limine aren't supported: they boot a kernel from `/boot` under one name that every deployment would share. The ESP has to be mounted somewhere other than `/boot`, `/efi` by default, since each deployment has its own `/boot`.

**Some disk layouts are refused.** The first switch lays the system out as deployments, and refuses before changing anything when `/boot`, `/usr`, `/opt`, `/var`, `/var/lib`, `/var/lib/pacman` or `/archix` is a separate filesystem, or the root is overlayfs, as in a container. Caches and logs on their own btrfs subvolumes, such as CachyOS's `@cache` and `@log`, are fine. See [Requirements](/docs/concepts/atomicity/#requirements).

**Hooks run before the network.** [Hooks](/docs/guides/hooks/), and `on_change` scripts of files in `/etc`, `/usr`, `/opt` and `/boot`, run at the new deployment's first boot, before networking and before anyone logs in. A hook that needs a running service, a network connection or a user's session fails there, and runs again at the next two boots; after three failures it waits for `archix hooks retry` or `archix hooks skip`.

**Package scripts get no network while staging on CachyOS.** CachyOS's pacman puts every install scriptlet and hook in a network namespace of its own, which it can't make inside archix's staging root, so archix gives the whole transaction one instead, with only loopback. A pacman hook with `NetworkAccess = allowed` gets no network there either. Arch's pacman runs as before.

**Leaving deployments needs the running deployment to be current.** [`archix eject`](/docs/reference/cli/#eject) turns the deployment you're running into a plain Arch root, but only when it's also the one the next boot starts. With a switch waiting for its reboot, reboot into it first, or roll back to the running one.

**The ESP needs room for one more boot image.** A [fallback image](/docs/concepts/atomicity/#the-fallback-boot-image) on the ESP boots `current` when a crash loses the whole `loader/entries` directory, which FAT allows. It's one more copy of a boot image, and a switch also needs room for the new deployment's images, one per installed kernel and one more with protected entries, while the booted and current ones stay. On a 512 MiB ESP with protected entries, even a `deployments.keep = 1` switch can be refused for space. 1 GiB, as the Arch installation guide suggests, is enough.

**A rollback keeps today's people, not package accounts.** `/etc/shadow` is part of each deployment's `/etc`. A rollback, and booting a deployment other than `current`, carry root's and regular users' entries and passwords into it by name, but package accounts stay as that deployment has them, and an account whose number another name has there isn't carried; the rollback names it.

**Some failures still need a live USB.** Rolling back to a kept deployment needs only the boot menu, and when no deployment boots, the [rescue entry](/docs/guides/recovery/#without-a-live-usb-the-rescue-entry) repairs filesystems, repoints current, resets passwords or ejects, without one. A live USB is still needed when the rescue entry can't start: an ESP the firmware can't read or that was wiped, a broken systemd-boot, Secure Boot refusing everything, or a machine that hasn't completed a switch since the rescue entry shipped. The steps are in [With a live USB](/docs/guides/recovery/#with-a-live-usb).

## Rollback

**A rollback keeps what's in `/var`.** Deployments hold `/usr`, `/opt`, `/boot`, `/etc`, pacman's database and DKMS state. Data under `/var`, such as databases, and your home are shared by every deployment and stay as they are. A newer PostgreSQL or MariaDB may have migrated its data, and the older version can't read it. `archix rollback` asks before going back across such versions, from a list it ships plus your [`unsafe_downgrades`](/docs/reference/options/#unsafe_downgrades), but picking an older entry in the boot menu boots it without asking; see [Downgrades that may break data](/docs/concepts/generations/#downgrades-that-may-break-data). Back up data you can't lose.

**Only kept deployments roll back instantly.** With the default [`deployments.keep = 2`](/docs/reference/options/#deploymentskeep), the previous deployment is kept. Older generations are rebuilt from the nearest kept deployment and their package files, which takes as long as an update and needs those files: in archix's cache, a [package cache](/docs/concepts/lockfile/#package-caches), the Arch Linux Archive, or, for third-party packages, archix's own copies.

**Boot counting needs systemd-boot 260 or newer, and stops at `boot-complete.target`.** A new deployment's entry gets [`boot.tries`](/docs/reference/options/#boottries) boots to reach `boot-complete.target`, after which systemd-boot starts the last deployment that booted. With an older systemd-boot on the ESP, archix writes plain entries, and a new deployment that hangs or panics stays the default: pick the previous one in the boot menu yourself. A deployment that gets that far but is broken past it, such as a desktop that doesn't start, counts as good. [`boot.health_check`](/docs/reference/options/#boothealth_check) moves the line for what it can check, units, listening ports, reachable hosts and logins, which suits servers; a host that's down for reasons of its own fails the check just the same, and falls back from a good update.

## Locking

**Third-party repo versions are exact only while a copy is cached.** Most third-party repos keep only the current build of each package. archix keeps a copy of everything it installs from them, but a fresh machine, or one whose cache was cleared, can only get what the repo serves today. Then the [fallback chain](/docs/guides/third-party-repos/#the-fallback-chain) picks a replacement and rewrites `archix.lock` with it, so the lock no longer says what the first machine had. A [package cache](/docs/concepts/lockfile/#package-caches) that the first machine fills, with `archix cache push` or after every switch with [`package_cache_push`](/docs/reference/options/#package_cache_push), closes the gap for every machine that can reach it, for as long as it keeps the files.

**Only git sources and downloads are pinned for AUR rebuilds.** An AUR package is locked to the commit of its build recipe, and its first build records in `archix.lock` the commit each git source was cloned at and the sha256 of each download whose checksums are `SKIP`; a later build of the same lock checks out those commits and checks those downloads. Sources from Mercurial, Subversion, Bazaar or Fossil aren't pinned: a rebuild takes whatever they serve that day, and `archix status` names such packages. Builds aren't bit-for-bit reproducible either, so another machine's build of the same pinned sources is the same code, not the same file, unless a [package cache](/docs/concepts/lockfile/#package-caches) it lists holds the first machine's build.

**Foreign packages init rebuilds stay on the machine they came from.** A package you built by hand, or one that left the AUR, is left in `ignored_packages` unless you pick it in [`archix init`](/docs/reference/cli/#init)'s wizard or with `--repack NAME`. A picked one becomes a recipe in [`pkgbuilds/`](/docs/guides/local-pkgbuilds-and-patches/) that names its installed files by sha256, while the files themselves stay in `/var/cache/archix/sources`, out of the config, and its builds stay out of package caches, since they may hold what isn't yours to share. So another machine sharing the config can't build it. A config file you edited goes into the recipe as the package shipped it, from the package file in pacman's, yay's or paru's cache, or not at all. Rebuilding needs every other file the package owns to be as pacman installed it, and the same of the foreign packages it depends on; init says why when one can't: `! nvidia-dkms-custom is in no repo or the AUR, and archix leaves it alone: usr/lib/modules-load.d/nvidia.conf changed since pacman installed it`.

## Trust and signatures

**Install scriptlets run as root.** Once you approve an AUR recipe, its package is installed by pacman like any other, and its install scriptlet runs as root inside the new deployment's staging tree. That tree is cut off from the running system, but the scriptlet can change anything in the deployment you'll boot. Review is the safeguard: a new package's review shows every file it ships, its `.install` file included, so read what that does before you trust a recipe.

**Rebuilding rollbacks trust the pinned sha256, not today's keyring.** In prepare, archix checks every package file against the sha256 in the lock, and has pacman check every incoming package's signature, so a bad signature or an unknown key stops a switch before anything changes. A rollback that rebuilds a dropped generation skips the signature: it installs packages that were verified when they were first installed, by the sha256 the generation pinned, so a packager key revoked since doesn't block going back. That also means a key revoked because it was compromised doesn't block it either. Packages archix built itself, from the AUR or your recipes, aren't signed; the lock and the build are what you trust.

**An AUR build the lock has no sha256 for is trusted as the cache says.** Packages from a [package cache](/docs/concepts/lockfile/#package-caches) are checked against the sha256 in the lock, like any download, AUR builds included: the lock records the first build of each recipe commit, and a cache's build of the same commit that differs is passed over. Until some machine has built it, as right after `archix update` locks a new commit, the lock has no sha256 for it, and archix takes the build the cache's record names, checked only against the record's own hashes. Whoever can write to the cache can hand your machines that package. List only caches you control.

## Secure Boot and the TPM

**Old signed boot entries stay bootable unless you revoke them, and revoking is experimental.** A copy of any UKI archix signed boots wherever it's put. [`archix secure-boot revoke`](/docs/guides/secure-boot/#revoking-old-boot-images) adds the ones archix no longer uses to `dbx`; it's tested on OVMF, not on real firmware, whose variable stores vary. It needs sbctl's KEK as a file, adds at most 128 entries, about a year or two of weekly kernel updates, past which old images stay bootable until a new db key retires them ([The dbx ceiling](/docs/guides/secure-boot/#the-dbx-ceiling)), and leaves old signed copies of systemd-boot alone. SBAT can't stand in: only shim enforces it ([Why not SBAT](/docs/guides/secure-boot/#why-not-sbat)).

**PCR 11 bindings break when the UKI changes; signed policies are experimental.** A switch that changes the kernel, initramfs or command line writes a new UKI, which measures differently into PCR 11, so a secret sealed to PCR 11's values has to be re-sealed. With systemd's PCR signing key in place, archix signs a policy into every UKI for secrets bound to the key ([TPM-bound secrets](/docs/guides/secure-boot/#tpm-bound-secrets)). A VM suite unlocks a LUKS volume bound that way with swtpm, under every UKI archix signed with the key and, after `archix secure-boot rotate-pcr-key`, only under those signed with the new one, but no test has used a real TPM yet, so don't rely on it for a disk you can't open otherwise.

**Which deployment boots isn't signed.** The UKIs and their command lines are signed. Which deployment a boot mounts comes from the boot menu entry, `loader/entries/archix-<n>.conf`, an unsigned file on the FAT ESP, which systemd-boot reports in the `LoaderEntrySelected` EFI variable. archix keeps a copy of every entry it writes on the root filesystem, and boots `current` when the entry that started has a name it didn't record, so a renamed entry doesn't move the system. An edited entry isn't checked against archix's copy when the deployment is mounted yet. Someone who can write to the ESP can still change `loader.conf` or the boot menu's EFI variables so that an older entry archix wrote starts, which boots that kept deployment; the boot menu offers it anyway. archix clears `LoaderEntryDefault` and `LoaderEntryPreferred`, which override `loader.conf`, whenever it writes `loader.conf`, and `archix status` warns while one is set.

**The signing keys sit on the root filesystem.** sbctl's Secure Boot keys, in `/var/lib/sbctl/keys`, and systemd's PCR signing key, `/etc/systemd/tpm2-pcr-private-key.pem`, are plain files that root can read, and so can anyone who mounts an unencrypted root from another system. With the db key they can sign a boot image your firmware accepts, with the KEK they can change `db` and `dbx`, and with the PCR key they can sign a policy that unlocks a secret bound with `systemd-cryptenroll --tpm2-public-key` for any UKI they build. Every older UKI archix signed also carries a valid signed policy, so it unlocks such a secret too until it's [revoked](/docs/guides/secure-boot/#revoking-old-boot-images), or the volume is bound to a new key with [`archix secure-boot rotate-pcr-key`](/docs/guides/secure-boot/#rotating-the-pcr-key). Package install scriptlets and hooks don't see the keys while a switch stages its deployment; only `ukify` does, to sign. Keep the root filesystem encrypted, and treat root on the machine as owning these keys; sbctl can keep its keys in a TPM or a YubiKey instead, though archix can't then sign `dbx` updates.

See [Secure Boot](/docs/guides/secure-boot/) for what archix does sign and check.

## Disk space

**A kept deployment costs an update's changed files.** With `deployments.keep = 2`, the previous deployment keeps every file the last switch replaced: 2.9 GB for a four-month update of 214 packages, 0.9 GB for a week's 36, on ext4 or btrfs, and 1.7 GB and 0.59 GB on btrfs with zstd. `deployments.keep = 1` costs the same as updating in place, once the new deployment has booted. Each kept deployment's boot image takes up to about 40 MB on the ESP. See [Storage](/docs/concepts/atomicity/#storage).

**The free-space check is an estimate.** Before a switch or rollback builds anything, archix checks every mount the incoming files land on, the way pacman does, from the file sizes in each package's `.MTREE` rounded up to whole blocks, plus a cushion; see [Signatures and disk space](/docs/concepts/safety/#signatures-and-disk-space). It doesn't count directories or a filesystem's own metadata. Official packages to download are counted ahead from the snapshot's repo databases; third-party packages and AUR builds from a package cache aren't, and a full cache disk stops the switch while those download, before anything changes. If the root fills up anyway while the deployment is built, the build fails and its staging tree is deleted; nothing was changed. Free inodes are checked too, roughly, on filesystems that report them; btrfs doesn't.

## Not yet known

- **Power-cut replay across every update.** Replaying every write to each flush point now covers archix's own switch, kept rollback, rebuild of a dropped generation and first boots, and the flaws it found are fixed. It passes on ext4 and btrfs on a desktop machine ([published evidence](https://github.com/archix-org/archix/releases/tag/powercut-evidence-8648816)), but hasn't yet passed on the release gate's slow nested VMs. It replays one prepared update, not every kind of transaction. On the ESP it tries up to 16 random subsets of the writes between two flushes; on the root, writes between flushes are replayed only in the order they were logged.
- **Weeks of use on real hardware.** The failure paths are exercised in VMs and containers: power-cut replay of archix's own switches, rollbacks and first boots, kills mid-switch, a full disk, a broken glibc, a revoked key, and a year of weekly switches with a reboot each. archix with deployments hasn't yet run for weeks on real machines, which is where the failures nobody thought to test turn up.
- **Upgrading from one release with deployments to the next.** A VM suite upgrades archix from an older build to a newer one through a switch, killed once halfway, and boots both; between releases it waits for a second release.
