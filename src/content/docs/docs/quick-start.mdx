This page takes you from a freshly installed archix to a declared, locked system with a few generations, one of which you've rolled back from. It takes about fifteen minutes, most of it reading what `archix init` found.

You need archix installed ([Installation](/docs/installation/)) and root access.

## Capture your system with `archix init`

You don't write your first config by hand. `archix init` reads your running system and writes a config and a lock that describe it exactly, down to the version of every installed package. It changes nothing on the machine except the config directory.

```console
$ sudo archix init
```

It opens a full-screen wizard in nine steps: Welcome, Config, Packages, System, Config files, Boot, Generations, Dotfiles and Review. Each step shows what init found and asks what it can't decide for you, with the recommended answer already chosen. You can go back and change any answer, and nothing is written until you choose `Write the config ›` on Review. Here's the Packages step:

```text wrap=false
 archix init                                                  host desktop  ·  step 3 of 9

 ✓ Welcome           │   Packages
 ✓ Config            │   What's installed, and what happens to what isn't declared.
 › Packages          │
   System            │   ✓ repos core, extra, multilib
   Config files      │   ✓ 86 packages declared, 3 from the AUR
   Boot              │   ✓ 2 Flatpak apps, locked to their installed commits: com.spotify.Client, org.mozilla.firefox
   Generations       │   · 2 dependencies that nothing needs any more: python-pip, rust
   Dotfiles          │
   Review            │     Dependencies nothing needs any more
                     │     › ● keep them (listed in ignored_packages)
                     │       ○ let the first switch remove them
                     │
                     │     Later, when you install something with plain pacman or yay
                     │       ● switch offers to declare it, and removes it if you say no (recommended)
                     │       ○ switch leaves it installed and only lists it
                     │
                     │     [x] Show each AUR build recipe and ask before trusting it
                     │
                     │     If a locked AUR version can't be built any more
                     │       ● ask, defaulting to the nearest newer version (recommended)
                     │       ○ take the nearest newer version
                     │       ○ take the nearest older version
                     │
                     │      ‹ Back     Next: System ›

 ↑↓ move  ·  enter choose  ·  esc back  ·  ←→ step  ·  q quit
```

The sidebar marks the steps you've seen with `✓` and the current one with `›`, and the header shows the host and the step. Focus moves one line at a time: every option of a choice, each `[x]` setting, each text field, each checklist entry, then the buttons. `›` marks the focused line, and the bottom line says what `enter` does there.

| Key | What it does |
| --- | --- |
| `↑` `↓`, `tab`, `shift-tab` | Move the focus to the next or previous line. From `Next`, `↓` reaches `‹ Back`. |
| `enter`, `space` | Act on the focused line: pick an option, switch a setting or checklist entry on or off, or start editing a text field. On a button, press it. |
| `←` `→` | Go to the previous or next step, like the buttons. On Review, `→` only focuses `Write the config ›`; it never writes. |
| `End` | Focus the `Next` button. |
| `esc` | Go back a step. |
| `a`, `n` | In a checklist, select all or none. |
| `r` | In a checklist, go back to the recommended entries: the recommended files in Config files and dotfiles in Dotfiles, everything in System's lists. |
| `q`, `ctrl-c` | Quit without writing anything: `init was cancelled; nothing was written`. |

Text fields (the config location and the generation limits) start empty, showing their default in gray, such as `/etc/archix (default)`; left empty, they keep it. They're edited in place: press `enter` on one, type, then `enter` keeps the value and `esc` puts the old one back. Only while you're editing do letters and digits go into the field, and the bottom line reads `type to edit  ·  enter done  ·  esc cancel`. Next and `→` refuse to leave a step whose text fields are invalid, and shows the problem above the key hints, such as `! the config directory must be an absolute path`. Steps with nothing to answer (Welcome and Review) start on Next, and `↑` `↓` scroll their content; every other step starts on its first field. Answers stay as you left them when you move between steps.

What each step decides:

<Steps>

1. **Welcome.** What init found: how many packages to declare and how many come from the AUR, config files, user accounts and Flatpak apps. Nothing to answer.

2. **Config.** `Where should the config live?` shows `/etc/archix (default)` until you type something else. Any directory works, such as a clone of your own repo. If you pick another directory, `/etc/archix` becomes a symlink to it, and a config inside your home is handed over to you, the whole tree including the `.git` below, so you can edit and commit it without `sudo`. When git is installed, `Make it a git repository` is on, and init runs `git init` and `git add -A` in the config directory; nothing is committed. `Write files read-only, like the Nix store (apps can't change them; a switch puts them back)` is off; turn it on to have archix write the files it manages read-only, as NixOS does, and put them back on every switch. See [Read-only files](/docs/guides/dotfiles-and-apps/#read-only-files).

3. **Packages.** Your explicitly installed packages, from the repos and the AUR, are declared in `installed.lua`. Third-party repos in your `pacman.conf`, such as CachyOS's or chaotic-aur, are declared as they are, and init asks what to do if a locked package disappears from one (see [Third-party repos](/docs/guides/third-party-repos/)). Foreign packages that aren't on the AUR, built by hand or gone from it, stay in `ignored_packages` unless you tick them, which rebuilds them as recipes in `pkgbuilds/` from their installed files, kept out of the config; one whose files changed since pacman installed it can't be, and a `!` line says why. Orphaned dependencies can be kept in `ignored_packages` or left for the first switch to remove. `Later, when you install something with plain pacman or yay` sets [`undeclared_packages`](/docs/concepts/pacman-and-yay/#undeclared-packages). With AUR packages, there are also review and [missing versions](/docs/concepts/lockfile/#missing-versions). System-wide Flatpak apps are declared in `flatpak.apps`, with any remote other than Flathub, and locked to the commits they're installed at. Apps installed with `--user` are left out, and so are apps whose remote is gone, with a `!` line. See [Flatpak and AppImages](/docs/guides/flatpak-and-appimages/).

4. **System.** Four checklists of what init takes over as it is, all ticked: `Settings` (hostname, timezone, locales and keymap where the option says what the files on disk do, comments aside; masked units and the default target), `Users` (regular users, uid 1000 to 59999, and system users made by hand rather than by a package's `sysusers.d`, each with uid, shell and groups, declared with their real groups, shell, home and description so declaring them changes nothing), `Groups` (regular groups and hand-made system ones, with their gid) and `Services that differ from their preset` (services, sockets, timers, targets and the like, each `enabled` or `disabled`). A setting the option can't say, such as a keymap next to `XKBLAYOUT` in `/etc/vconsole.conf`, gets a `!` line and its file is offered in Config files instead. Untick anything archix should leave alone; it isn't declared. Passwords stay where they are; archix never manages them.

5. **Config files.** The `/etc` files you changed: package config files edited since they were installed, and every file and symlink in `/etc` nobody owns, but for pacman's `.pacnew` and `.pacsave` files, backups and generated files. Unit files someone put in `/usr/lib/systemd/system` by hand come too, as copies for `/etc/systemd/system`, since a deployment's `/usr` holds only what packages install. Files that hold secrets are never copied; they're named, a directory such as `/etc/wireguard/` as one line, so you know what to bring along yourself. The rest is one scrollable checklist, each file tagged with why it's there: `recommended`, then `changed from its package's version` or `not from any package`. Recommended files, such as `/etc/fstab` and anything hand-written, start ticked; the others are mostly changed by package install scripts. See [Safety](/docs/concepts/safety/#what-init-captures-and-never-captures).

6. **Boot.** archix boots every generation as its own [deployment](/docs/concepts/atomicity/), so it needs systemd-boot. If systemd-boot is installed and your kernel command line has `root=`, the step shows the command line and offers `Boot every generation as its own deployment, from a systemd-boot entry`, on. Left off, `archix switch` refuses. The Result section later says whether the first switch can lay the system out as deployments, and why not if it can't, such as an ESP mounted at `/boot`; then the summary ends with `! Before the first switch:` and what to change, instead of `Next:`.

7. **Generations.** `Generations gc always keeps`, shown as `10 (default)`, and `…and any younger than this many days`, shown as `30 (default)`. Leave them empty for the defaults; anything you type has to be a whole number.

8. **Dotfiles.** Pick a user if there's more than one, then choose entries from `~/.config` and top-level dotfiles. Recommended ones, such as your shell's rc files, `.gitconfig`, and editor, terminal and window manager configs, start ticked; untick everything to bring in none. Caches, browsers and app state aren't offered, and credentials such as `~/.ssh` are only counted. Ticked entries are copied into the config's `home/`. Directories become live links, and so do files, unless you turned on read-only files, which makes them read-only copies instead. Files their app replaces on save, such as KDE's `*rc` files and `mimeapps.list`, always become writable copies, since a link wouldn't survive the app's save. See [Dotfiles and apps](/docs/guides/dotfiles-and-apps/#bringing-your-existing-dotfiles-in).

9. **Review.** Everything init will write, one line each: the config location, packages, undeclared and unused packages, Flatpak apps, accounts, services (`3 of 4` when you unticked one), config files, boot, generations and dotfiles. `Write the config ›` writes it.

</Steps>

Then the wizard closes, and init prints the rest in the terminal. With AUR review on, it shows each AUR build recipe and asks before trusting it. It finds the Arch Linux Archive snapshot that matches the most installed versions and pins every package that differs from it, older ones included, so the lock is exactly what you have (see [The lockfile](/docs/concepts/lockfile/#how-init-picks-the-snapshot)). Then it shows what the first switch would change, which should be nothing:

```
── Lock ────────────────────────────────────────
  · finding the archive snapshot closest to what's installed
  ✓ 212 packages locked to the 2026-10-09 snapshot
  · held at their installed version instead: mesa
  ✓ 2 Flatpak apps locked to their installed commits

── Result ──────────────────────────────────────
  ✓ the system matches the lock and the config: the first switch changes nothing

  Config written to /etc/archix
    init.lua                          loads this host
    lua/hosts/desktop/init.lua        settings, users, services and files
    lua/hosts/desktop/installed.lua   packages; archix -S and -R edit it
    files/desktop/                    copies of the managed config files
    archix.lock                       the exact package versions

  Next: look it over, then run sudo archix switch
```

For scripts, `sudo archix init --defaults` takes every recommended answer without opening the wizard, so it needs no terminal. It ticks the recommended config files, never imports dotfiles, makes the config directory a git repository when git is installed, and prints what it captured in Packages, System, Config files, Boot and Generations sections before the same Lock and Result. The config files you didn't get are listed by path, so you can add them to `files` or run the wizard later to pick them, and so are the secrets it left out.

There are two exceptions to an empty Result. Dotfiles you imported are listed, because the first switch backs up the originals and replaces them with links into the config. And archix declares the boot tooling it needs, `mkinitcpio`, `systemd-ukify` and `dosfstools`, so the Result lists them as installs if they're missing. Either way, the section starts with `! the first switch would still change these:`.

## Look at what you got

The config is laid out like a neovim config:

```console
$ tree /etc/archix
/etc/archix
├── archix.lock
├── init.lua
├── files
│   └── desktop
│       └── etc
│           ├── fstab
│           ├── mkinitcpio.conf
│           ├── pacman.d
│           │   └── mirrorlist
│           └── sysctl.d
│               └── 80-swappiness.conf
└── lua
    └── hosts
        └── desktop
            ├── init.lua
            └── installed.lua
```

`init.lua` imports the host that matches your hostname. `lua/hosts/<hostname>/init.lua` holds what init captured:

```lua title="lua/hosts/desktop/init.lua"
-- Written by `archix init` from this machine; edit it freely.
return {
  hostname = "desktop",
  timezone = "Europe/Berlin",
  repos = { "core", "extra", "multilib" },
  ignored_packages = { "nvidia-dkms-custom" },
  flatpak = { apps = { "com.spotify.Client", "org.mozilla.firefox" } },
  users = {
    me = { uid = 1000, groups = { "wheel" }, shell = "/usr/bin/zsh", description = "Me" },
  },
  services = { ["bluetooth.service"] = true, ["sshd.service"] = true },
  files = {
    ["/etc/fstab"] = { source = "files/desktop/etc/fstab" },
    ["/etc/sysctl.d/80-swappiness.conf"] = { source = "files/desktop/etc/sysctl.d/80-swappiness.conf" },
    -- ...
  },
  kernel_params = { "root=UUID=0a3c5e1f-6b2d-4f7a-9c8e-1d2b3a4c5e6f", "rw", "quiet" },
  boot = { loader = "systemd-boot" },
}
```

Your explicitly installed packages, from the repos and the AUR, are in `installed.lua`. The file is yours to edit freely; `archix install` and `archix remove` add and remove names there too, as its first line says. Dependencies aren't listed; the lock records them.

```lua title="lua/hosts/desktop/installed.lua"
-- This host's packages. Edit freely; `archix install` and `archix remove` add and remove names here too.
return {
  packages = {
    "base",
    "firefox",
    "linux",
    -- ...
  },
}
```

`archix.lock` holds the snapshot date and every package's exact version. Packages that didn't match the snapshot are listed under `pinned`, and Flatpak apps get their own table with the commit each is installed at:

```toml title="archix.lock"
[hosts.desktop]
date = "2026-10-09"
repos = ["core", "extra", "multilib"]
declared = ["archix", "base", "dosfstools", "firefox", "linux", "mkinitcpio", "neovim", "steam", "systemd-ukify"]
pinned = ["mesa"]

[hosts.desktop.packages]
firefox = { version = "144.0-1", repo = "extra", file = "firefox-144.0-1-x86_64.pkg.tar.zst", sha256 = "37895f9d195203f4981ee730bec23c4079d10b5b53fc2c3e69db37c1bfed1257", explicit = true }
# ...

[hosts.desktop.flatpak]
"com.spotify.Client" = { remote = "flathub", ref = "app/com.spotify.Client/x86_64/stable", commit = "5f8806197a2b3c4d6e8f0a1b2c3d4e5f60718293a4b5c6d7e8f9012a3b4c5d6e" }
"org.mozilla.firefox" = { remote = "flathub", ref = "app/org.mozilla.firefox/x86_64/stable", commit = "0bb3a9e40c1f8d2e4b6a7c9d1e3f5a7b9c0d2e4f6a8b1c3d5e7f9a0b2c4d6e8f" }
```

git is optional, but worth it. When the config directory is a git repo, every generation records the commit it was built from. If git is installed and you left `Make it a git repository` on, `init` already ran `git init` and `git add -A`, so commit now, from the config directory (with `sudo` if it's the root-owned `/etc/archix`):

```console
$ git add -A && git commit -m "Capture desktop with archix init"
```

## The first switch

```console
$ sudo archix switch
lay out   the system as deployment 1: /usr, /etc, /opt, /boot and pacman's database move into /archix/deploy/1, with a boot entry of its own
apply 1 change? [Y/n]
:: laying the system out as deployment 1
laid the system out as deployment 1, which boots from its own entry; changes from now on take effect at the next boot
switched to generation 1 (snapshot 2026-10-09); its deployment boots at the next restart
```

No packages change. The first switch lays your system out as deployment 1, in `/archix/deploy/1`, and gives it a boot entry: hardlinks on ext4 and a snapshot on btrfs, so it costs little space. The files archix took over are backed up first, so taking one out of the config later puts the original back. Reboot once, so the machine starts from deployment 1's entry. Your system looks the same as before, but now it's described, locked and reversible.

From here on, `/usr` is read-only and every switch builds the next deployment beside the running one. It takes effect at the next boot. See [Atomic deployments](/docs/concepts/atomicity/).

## Make a change

Add a package to your host file. Lists from every module are concatenated, so this adds to what's in `installed.lua`:

```lua title="lua/hosts/desktop/init.lua" ins={3}
return {
  hostname = "desktop",
  packages = { "htop" },
  -- ...
}
```

Ask archix what that would do before doing it:

```console
$ archix diff
resolving 87 declared packages against the 2026-10-09 snapshot
note: archix.lock is out of date for desktop; showing a fresh resolution
snapshot 2026-10-09: 213 packages
install    htop 3.4.1-1
```

The lock still has your old package set, so `diff` resolves the new one on the fly. `htop` comes from the same 2026-10-09 snapshot as everything else, so adding it doesn't upgrade anything else. That is the point of the snapshot.

Now switch:

```console
$ sudo archix switch
resolving 87 declared packages against the 2026-10-09 snapshot
+ htop 3.4.1-1
213 packages locked
wrote /etc/archix/archix.lock
install    htop 3.4.1-1
a new deployment with its own boot entry; it boots at the next restart
apply 2 changes? [Y/n]
downloading htop-3.4.1-1-x86_64.pkg.tar.zst
:: building deployment 2 from deployment 1
...
hibernation is off until you reboot into deployment 2: resuming would start its kernel on the running system's memory image; suspend still works
switched to generation 2 (snapshot 2026-10-09); its deployment boots at the next restart
deployment 2 is committed and boots at the next restart; changes to /etc made before then are carried over to it
```

`switch` updated the lock for you, showed the changes, and built deployment 2 once you said yes. The running system doesn't change: reboot, and `htop` is there. Until you do, changes you make to `/etc` are carried into the new deployment, and hibernating is off. `sudo archix install htop` would have done the same, writing the name to `installed.lua` instead of your host file. Commit the change:

```console
$ git commit -am "Add htop"
```

## Update everything

To move to today's packages, update the lock to the newest archive snapshot, then switch. `update` only rewrites the lock; nothing is installed until you switch:

```console
$ sudo archix update
resolving 87 declared packages against the 2026-10-15 snapshot
snapshot 2026-10-09 -> 2026-10-15
~ linux 7.2.8.arch1-1 -> 7.2.9.arch1-1
~ mesa 1:25.3.0-1 -> 1:25.3.1-1
213 packages locked
wrote /etc/archix/archix.lock
$ sudo archix switch
...
switched to generation 3 (snapshot 2026-10-15); its deployment boots at the next restart
```

Reboot into generation 3. You can also use `sudo archix -Syu`, or just `sudo archix`, which does both in one go, like yay. See [pacman and yay](/docs/concepts/pacman-and-yay/#archix--syu).

## Roll back

Say the new mesa breaks your games. Go back:

```console
$ sudo archix rollback
generation 2 (snapshot 2026-10-09) still has its deployment: rolling back points current and the boot default at it, nothing is reinstalled
downgrade  linux 7.2.9.arch1-1 -> 7.2.8.arch1-1
downgrade  mesa 1:25.3.1-1 -> 1:25.3.0-1
roll back to generation 2 (snapshot 2026-10-09)? [Y/n]
rolled back to generation 2 (snapshot 2026-10-09); it boots at the next restart. archix.lock is unchanged, so the next `archix switch` returns to the config
```

Deployment 2 is still there, so the rollback only points the boot default at it. Reboot, and you're on generation 2 with the same packages, kernel and `/etc` it had. Nothing is reinstalled.

Rollback changes the system, not your config. Your `archix.lock` still says 2026-10-15, so the next `archix switch` would apply it again. To stay back, revert the lock in git, or move it with `archix update --to 2026-10-09`.

<Aside type="tip">
	If the system won't boot at all, pick generation 2 in the systemd-boot menu. It boots that deployment, and archix makes it current. See [Generations and rollback](/docs/concepts/generations/#rolling-back-from-the-boot-menu).
</Aside>
