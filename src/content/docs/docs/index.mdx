archix is a system configuration tool for Arch Linux and Arch-based distros. CachyOS is the first-class target. Other Arch-based systems such as EndeavourOS should work, but only Arch and CachyOS are tested. You describe the whole machine in Lua: packages from the official repos, the AUR and third-party repos like CachyOS, plus `/etc` files, systemd units, users, kernel parameters and dotfiles. archix makes the system match that description, records exactly what it installed in a lockfile, and keeps every switch as a generation you can roll back to.

If you know NixOS, the idea is familiar: a declarative config, a lockfile and rollback. The difference is that archix runs on Arch's real packages and the AUR. There is no Nix store, no derivations and no second package ecosystem to learn.

```lua title="/etc/archix/lua/hosts/desktop/init.lua"
return {
  repos = { "core", "extra", "multilib" },
  packages = { "firefox", "steam", "neovim" },
  users = { me = { groups = { "wheel" } } },
  home = { user = "me" },
  programs = { kitty = { enable = true, settings = { font_size = 11 } } },
}
```

```console
$ sudo archix switch
```

That's the loop: edit Lua, switch, reboot into the result, and roll back if you don't like it. You don't start from an empty file, either: `sudo archix init` captures the machine you already have into a config and a lock that match it exactly, but for the secrets and files it leaves out, which `archix diff` keeps naming.

## Three pillars

### Declared

Your config lives in `/etc/archix` by default and is laid out like a neovim config: an `init.lua`, one module per host, and modules you share between hosts. Options have types, defaults and descriptions, and archix rejects anything it doesn't know:

```console
$ archix diff
error: `programs.kity`: option does not exist (set in lua/hosts/desktop/init.lua); did you mean `programs.kitty`?
```

Evaluation is pure. Your Lua can't run commands or read random files, so the same config and lock give the same system on every run. The exception is what you set up by hand and never declared, such as a tree under `/opt` no package installed, an edited config file or SSH host keys: each deployment starts as a copy of the one before, so it stays on that machine, but a machine built from the config won't have it. `archix diff` and `archix status` [name it](/docs/reference/cli/#carried-but-not-declared). Read more in [Configuration](/docs/concepts/configuration/).

### Locked

Arch is a rolling release. "Install git" means something different every day. archix pins your official packages to one day of the [Arch Linux Archive](https://archive.archlinux.org), so "install git" means "install git as it was on 2026-10-14", for as long as you want it to:

```toml title="archix.lock"
version = 1

[hosts.desktop]
date = "2026-10-14"
repos = ["core", "extra", "multilib"]
declared = ["firefox", "git", "neovim", "steam"]

[hosts.desktop.packages]
git = { version = "2.51.0-1", repo = "extra", file = "git-2.51.0-1-x86_64.pkg.tar.zst", sha256 = "e6674e96c7bbc318a40c1fd0008a6b00688683ce3d1b324544ebc9380885d098", explicit = true }
```

You move forward when you choose to, with `archix update`. Read more in [The lockfile](/docs/concepts/lockfile/).

### Reversible

A switch first prepares everything (the lock, AUR builds, downloads, rendered files) without touching the system. Then it builds a complete new deployment beside the running one and commits it in one step, designed so a power cut at any moment leaves the old system or the new one, never a mix; the new one starts at the next boot. The result is a generation: the exact package set, the managed files, users and services, and the git commit of your config. If a generation turns out bad, `archix rollback` takes you back. If it won't boot, pick the previous entry in systemd-boot, and it boots with the same packages, kernel and `/etc` it had, with nothing reinstalled. Read more in [Atomic deployments](/docs/concepts/atomicity/), [Generations and rollback](/docs/concepts/generations/) and [Safety](/docs/concepts/safety/), and see [Limitations and failure modes](/docs/concepts/limitations/) for where the guarantees stop. [Feature status](/docs/concepts/status/) says which features are shipped, partial or planned, and what tests each.

## How it relates to pacman, yay and NixOS

**pacman** still does the installing. archix runs every transaction through the `pacman` binary, inside the deployment it's building. The running system's `/usr` is read-only, so plain `pacman -S` and `-Syu` don't change it any more; `pacman -Q` and `-Ss` work as always. See [pacman and yay](/docs/concepts/pacman-and-yay/).

**yay and paru** are replaced. archix is an AUR helper with the flags you already type: `archix -S`, `archix -Ss`, `archix -Syu`, `archix -R`, and bare `archix` for a full update. The difference is that AUR build recipes are shown for review, locked by commit, built in a clean chroot and added to your config. See [The AUR](/docs/guides/aur/).

**NixOS** is the inspiration. Priorities, the module system and the generation model will feel familiar, and archix's priorities even use the same numbers. See [Coming from NixOS](/docs/guides/coming-from-nixos/).
